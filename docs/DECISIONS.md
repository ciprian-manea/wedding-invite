# Decisions

Append new decisions at the bottom: date, decision, why. Never rewrite old entries.

- 2026-10-18 · Opening is a pre-rendered video, not CSS/3D. Why: identical look on every phone, cinematic quality, simple code.
- 2026-10-18 · Music runs through Web Audio with a GainNode. Why: iOS ignores `audio.volume`, so fades need Web Audio.
- 2026-10-18 · Guest name is HTML over the poster, not baked into the video. Why: one video serves every guest.
- 2026-10-18 · H.264 MP4 in two sizes, no HEVC-only. Why: HEVC fails on many Android/Chrome devices.
- 2026-10-18 · Content in JSON files validated by Zod, no database in v1. Why: fastest path; the loader is the only thing to swap later.
- 2026-10-18 · Only `motion` for animation. Why: one library, React-friendly, enough for reveals and scroll effects.
- 2026-10-24 · `loadContent()` is marked `"use cache"`; `/demo` is marked `export const instant = false`. Why: this Next.js version (16, Cache Components on by default) errors at build/dev time on uncached file reads and on reading `searchParams` outside `<Suspense>` during prerendering. The content JSON read is static and cacheable; the page itself is genuinely per-request (guest line and language come from the URL), so it's marked as an allowed blocking route rather than forced into a Suspense shell for a single-route draft.
- 2026-10-24 · Browser-only state that affects which elements mount (session-storage "stay revealed", `prefers-reduced-motion`) is read with `useSyncExternalStore`, not `motion`'s `useReducedMotion()` or a plain `useEffect` + `setState`. Why: both of the obvious alternatives are unsafe here — `useReducedMotion()` returns `null` on the server and the real value immediately on the client's first render, so gating the opening video's mount on it caused a real hydration mismatch (confirmed in testing); a `useEffect` that calls `setState` to restore the value after mount works but is flagged by the project's `eslint-plugin-react-hooks` lint rule and causes an extra render. `useSyncExternalStore` with a server snapshot of `false` renders identically on the server and the first client pass, then updates safely right after hydration — the correct tool for "value only knowable in the browser, used to decide what renders."
- 2026-10-26 · `lib/useReducedMotion.ts` (a `useSyncExternalStore` wrapper, same pattern as the entry above) is the only way any component reads reduced-motion, not `motion`'s own `useReducedMotion()`. Why: M2's section components originally called `motion`'s hook directly to vary `initial`/style values (rise distance, scale, scaleY) passed to `motion.*` elements. Those values get baked into the server-rendered `style` attribute too, not just used to decide what mounts — so the same null-vs-real-value gap documented above caused real hydration mismatches there as well (reproduced with Playwright's `prefers-reduced-motion: reduce` emulation), not only in the mount-gating case. The shared hook is now the single safe source for this value anywhere it feeds a rendered style, not just anywhere it gates a mount.
- 2026-10-26 · Every `motion.*` element whose `initial` pose is computed from `reducedMotion` (`Reveal`, `Cover`'s letter spans, `Story`'s photos, `Schedule`'s timeline items, `DressCode`'s dots) carries a `key` that includes `reducedMotion`. Why: fixing the hydration mismatch above (by having the hook always resolve to `false` on the very first client render, matching the server, then update) revealed a second, separate bug — `motion`'s `initial` prop is captured once at mount and never re-applied, so an element that mounts during that first `false` pass stays frozen with the "full motion" start pose even after the hook corrects itself moments later. Caught by the mobile-qa subagent: under a real `prefers-reduced-motion: reduce` device, below-the-fold sections still rose/scaled/rotated into view on first reveal instead of just fading. Keying on the resolved value forces React to remount the element once the real value is known — before any guest could plausibly scroll to it — which re-evaluates `initial` correctly without reintroducing the hydration mismatch (the remount happens client-side only, after hydration has already committed).
- 2026-10-26 · `ScratchReveal`'s cover canvas is sized with a `ResizeObserver` on its container, not a one-time `container.clientWidth` read plus a `window.addEventListener("resize", …)` fallback. Why: the one-time read raced with layout — under the remount behavior from the decision above (a reduced-motion guest's `Reveal` wrapper, and everything inside it including `ScratchReveal`, remounts shortly after first paint), the read could land before the new instance's container had a real size, leaving the canvas at 0×0 and `getImageData` throwing `IndexSizeError` every 200ms. `ResizeObserver` fires once immediately with the container's actual current size whenever layout has genuinely settled, and again on every later resize, which is simply the correct tool for "give me an element's size, now and whenever it changes" — plus a defensive zero-size guard in both the paint and the clear-percentage check, in case a transient zero-size moment ever recurs for an unrelated reason.
- 2026-10-26 · Language switching updates `document.documentElement.lang` and the URL's `?lang=` via a plain `useEffect` + `history.replaceState`, not `next/navigation`'s `useSearchParams`/`useRouter`. Why: `useSearchParams` requires a `<Suspense>` boundary to avoid a full client-side-render bailout during static generation; `/demo` is already forced fully dynamic (`export const instant = false`, see the 2026-10-24 entry above) specifically to allow reading request-time `searchParams` server-side, so adding a second, client-side searchParams API into the same route risked fighting that existing arrangement for no real benefit. `history.replaceState` is a plain, dependency-free browser API that does exactly what's needed (update the URL without a navigation) and matches the project's existing preference for try/catch-wrapped direct browser APIs over framework abstractions for this class of "browser-only, best-effort" behavior.
- 2026-10-26 · `designs/jardin-blanc/theme.ts` gained a `--color-error` token, and the shared `Button`/`ButtonLink` plus RSVP's form inputs and yes/no toggle carry `scroll-mb-[calc(env(safe-area-inset-bottom)+76px)]`. Why: the mobile-qa subagent found the fixed mute/language-switch chrome (bottom ~60px of the viewport, see Invitation.tsx) could land on top of the RSVP submit button — reproduced with `submit.scrollIntoView({block:"end"})`, which matches what mobile Safari/Chrome do when auto-scrolling a focused field above the keyboard, so this was a realistic collision, not a contrived one. `scroll-margin-bottom` is respected by both `scrollIntoView()` and that focus-driven auto-scroll, so reserving it on every button/input clears the chrome without touching normal manual scrolling. The error color was a separate, smaller finding from the same review pass: form validation text was hardcoded as Tailwind `red-600` instead of a theme variable.
- 2026-10-27 · M4 accessibility pass: `--color-ink-soft` (`#7A7266`→`#766E63`) and `--color-accent` (`#7E8F6E`→`#667359`) were both darkened to clear WCAG AA's 4.5:1 text-contrast minimum on `--color-paper` (previously 4.25:1 and 3.12:1) — confirmed by computing relative luminance directly rather than eyeballing it. `accent` mattered beyond the script headings it was designed for: `Button`'s 13px label text reuses it too, so it was a real legibility gap for the pill buttons guests actually tap, not just a decorative shortfall. The owner chose this over a two-tone split (keep the lighter sage for large headings, introduce a separate darker color just for small text) to keep one accent color across the design rather than two. Values chosen by binary-searching HSL lightness at fixed hue/saturation for the minimum darkening that clears 4.5:1, to stay as close as possible to the original sage.
- 2026-10-27 · `SectionTitle`, `Cover`'s couple-name heading, `Footer`'s monogram, and `ScratchReveal`'s revealed-date text all set `font-family: var(--font-script), var(--font-serif)` (both CSS variables chained in one property), not `var(--font-script)` alone. Why: Pinyon Script has no Cyrillic glyphs (confirmed against Google Fonts' own metadata) — with only the script font specified, the browser's normal per-character fallback silently substitutes the OS's default serif for any Cyrillic character, so every Russian section heading was rendering in a random system font instead of this project's own typography, with no console warning to catch it. Chaining in Cormorant Garamond (already loaded, already Cyrillic-subsetted per `app/layout.tsx`) as the fallback keeps Russian headings on-brand; it reads as an elegant serif rather than a script for Cyrillic text specifically, which is an honest, accepted limitation rather than sourcing a second, Cyrillic-capable script font for this draft. (The spec-reviewer subagent caught that the first pass at this fix missed `ScratchReveal`'s date text, which is also Cyrillic in `ru` via `lib/date.ts`'s `Intl.DateTimeFormat`.)
- 2026-10-27 · Open Graph/title metadata moved from a hardcoded object in `app/layout.tsx` to a `generateMetadata` export in `app/demo/page.tsx` that reads `content/demo.json`; the root layout keeps only a generic fallback title/description and no `openGraph` block at all. Why: the project's own rule is that wedding text comes from content JSON, not components — adding a second hardcoded `openGraph` object next to the pre-existing hardcoded `title`/`description` (both from an earlier milestone) would have doubled the surface needing a manual update per wedding, when `docs/PROJECT.md` already commits to "a second wedding = a new JSON file + new media, no code changes." `generateMetadata` reads the couple's names and the cover section's subtitle (already localized content) for the title/description, and builds the OG image path from `content.design` rather than a hardcoded `jardin-blanc` path.
- 2026-10-27 · `content/demo.json`'s `dressCode.palette` third swatch was updated from `#7E8F6E` to `#667359` to match the accent-color darkening above; `docs/ART_BRIEF.md`'s sage reference was deliberately left at the original `#7E8F6E` and not touched. Why: the DressCode swatch is rendered live on the same page as the UI's actual accent-colored buttons/titles, so leaving it stale would create a visible, confusing mismatch between "the app's sage" and "the dress-code's sage." The art brief's sage value describes the _photographed_ wax seal in generated artwork — a physical/photographic color choice with no text-contrast requirement — so the accessibility-driven darkening doesn't apply there; conflating the two would needlessly shift the art direction for no benefit.
